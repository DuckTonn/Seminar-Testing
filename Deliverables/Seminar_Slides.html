API Testing là gì?
Kiểm thử trực tiếp giao diện lập trình ứng dụng (API), bỏ qua giao diện đồ họa (GUI).
Hiểu đơn giản: API như "Người phục vụ"
Khách hàng (Frontend)
Là bạn đang ngồi ở bàn, xem thực đơn và gọi món (Gửi Request).
Nhà bếp (Backend / Database)
Nơi lưu trữ nguyên liệu và chế biến món ăn theo yêu cầu.
Người phục vụ (API)
Nhận order từ bạn, mang vào bếp. Bếp làm xong, người phục vụ mang món ăn (Response) ra cho bạn. API Testing là tự bạn đi nói chuyện với phục vụ mà không cần thực đơn.
Tại sao API Testing lại quan trọng?
Phát hiện lỗi sớm (Shift-left)
Không cần chờ Frontend làm xong UI mới có thể test Backend.
Kiểm tra Bảo mật (Security)
Rất nhiều hacker vượt qua giao diện Web/App để tấn công thẳng vào API (Bypass UI). API Testing giúp bít lỗ hổng này.

Giải phẫu một API Request & Response
Hiểu rõ 5 thành phần cấu tạo nên một giao tiếp API chuẩn RESTful.
Thành phần Ý nghĩa và Ví dụ
1. Endpoint & URL Địa chỉ định danh tài nguyên trên server. VD: http://localhost:3000/api/products.
2. HTTP Method Hành động muốn thực hiện. GET (Lấy), POST (Tạo mới), PUT (Cập nhật), DELETE (Xóa).
3. Headers Siêu dữ liệu (Metadata). Quan trọng nhất là Authorization: Bearer <token> để xác thực danh tính.
4. Payload (Body) Dữ liệu gửi lên server (thường định dạng JSON). VD: { "price": 50000 }.
5. Status Code Mã phản hồi từ server. 200 OK (Thành công), 400 Bad Request (Lỗi dữ liệu gửi lên), 404 Not Found, 500 Internal Error (Server sập).
Lưu ý: Một API Test đúng chuẩn phải kiểm tra đầy đủ cả Status Code lẫn Cấu trúc dữ liệu Response trả về.

Postman Failure Modes — điểm mù của tool
Các lỗi thường gặp do công cụ, dễ gây hiểu lầm cho người test.
Failure mode Mô tả & Cách phòng tránh
Sai kiểu dữ liệu (Type Coercion) API trả về String "100", nhưng logic test yêu cầu Number 100. Việc xài toán tử lỏng lẻo == sẽ khiến Postman báo Pass ảo. Phải dùng === hoặc kiểm tra type cụ thể.
Quên chọn Environment Gửi URL hoặc Token chứa chuỗi chưa được parse (VD: {{baseUrl}}), dẫn đến API sập nhưng mất thời gian debug sai hướng. Lỗi do người dùng.
Silent Failure trong Script Viết sai cú pháp JavaScript (VD: pm.jsson() thay vì pm.response.json()), môi trường Sandbox của Postman bỏ qua lỗi và ngừng thực thi script bên dưới. Giao diện không báo đỏ — tạo ra Ảo giác Pass nguy hiểm.
Bài học: Luôn kiểm tra kỹ biến môi trường và sử dụng linter hoặc mở Postman Console (Ctrl+Alt+C) để debug script ngầm.

8 · Năng lực của AI
Slide 8 / 21
EShop Seminar · T06_API_and_Contract_Testing
AI Failure Modes
Nhận diện các rủi ro nguy hiểm khiến kết quả kiểm thử bị sai lệch (False Positive) khi mù quáng tin vào AI.
Failure Mode Hiện tượng & Hậu quả
Schema Validation lỏng lẻo AI thường sinh schema dạng "properties": {} và "additionalProperties": true. Lỗi này khiến thư viện ajv chấp nhận mọi dữ liệu trả về (kể cả khi rò rỉ dữ liệu). Gây ra False Positive cực kỳ nguy hiểm.
Bỏ qua Business Rules (Quy tắc kinh doanh) AI chỉ có "thiên kiến Happy-path". Hoàn toàn bỏ qua các kịch bản hóc búa (Edge Cases) như: 1 người dùng xài Coupon nhiều lần, hay giỏ hàng âm vẫn Checkout. Hệ thống trả về 200 OK nhưng doanh nghiệp đang lỗ nặng.
Xung đột Dữ liệu Tĩnh AI hay gắn cứng (hardcode) giá trị vào payload (VD: email: "test@domain.com"). Chạy test lần 1 thì Pass, nhưng chạy lại lần 2 trên CI/CD sẽ sập do lỗi trùng Email trong Database (Conflict 409).
Bài học: AI chỉ tạo Boilerplate. Con người (Human-in-the-loop) phải tự review mã nguồn và thiết kế kịch bản bẻ khóa nghiệp vụ.

Chiến lược Prompt Engineering — 4 Bước Chuỗi Mắt Xích
Mỗi prompt giải quyết đúng một điểm mù của AI. Đầu ra prompt trước là đầu vào của prompt sau.
Prompt 1 → Khởi tạo Skeleton
Đính kèm API Specification + yêu cầu bao phủ đầy đủ
AI sinh toàn bộ Collection v2.1.0: URL, Headers, Body, test script status cơ bản. Tiết kiệm 80% thời gian setup thủ công.
Prompt 2 → Siết Schema
Ép AI viết schema chặt: required + additionalProperties: false
Khắc phục Schema Validation rỗng — nguyên nhân chính gây ra False Positive nguy hiểm trong CI/CD.
Prompt 3 → Negative & Security
Ép AI đóng vai Penetration Tester
Sinh kịch bản không có token, token hết hạn, leo thang đặc quyền (RBAC), dữ liệu sai kiểu, giá trị biên âm/0.
Prompt 4 → Chaining & Dynamic Data
Trích xuất ID → lưu biến môi trường → truyền tự động
Sinh dữ liệu ngẫu nhiên (random email/UUID) để chạy lặp CI/CD không bị Conflict 409. Kiểm tra vòng đời dữ liệu xuyên suốt.

AI vs Manual Testing — So sánh Thực tiễn
Chiến lược tối ưu: Human-in-the-loop — AI tăng tốc, QA đảm bảo chất lượng.
Tiêu chí AI (Prompt Engineering) QA Engineer (Manual)
Tốc độ khởi tạo ✓ < 1 phút — Parse spec, sinh JSON skeleton ngay lập tức Hàng giờ — gõ tay từng URL, Header, Body
Độ bao phủ Edge Cases ✗ Thấp — Thiên kiến Happy-path, bỏ sót giá trị biên ✓ Cao — Tư duy phản biện, nhận diện rủi ro nghiệp vụ
Schema Validation ✗ Lỏng lẻo — Sinh properties: {} gây False Positive ✓ Chặt chẽ — Định nghĩa rõ required, additionalProperties: false
Request Chaining ✗ Nông — Test từng request riêng lẻ, hardcode dữ liệu ✓ Sâu — Chuỗi liên kết, kiểm tra vòng đời dữ liệu
Kết luận: Dùng AI để sinh Boilerplate nhanh (80% thời gian setup) → QA Review và bổ sung Edge Cases, Security Tests, Business Rules → Pipeline CI/CD an toàn.

Integration Testing vs Contract Testing
Hiểu rõ nỗi đau của Integration Test truyền thống và cách Contract Test (Pact) giải quyết triệt để.
Integration Testing (E2E)
Phức tạp & Nặng nề
Để test kết nối FE-BE, bạn cần phải dựng cả Frontend, Backend, Database chạy cùng lúc. Tiêu tốn hàng GB RAM trên môi trường CI.
Flaky (Dễ gãy) & Khó debug
Test thất bại vì một service bên thứ 3 (như cổng thanh toán) phản hồi chậm chứ không phải do code của bạn sai. Mất hàng giờ mò log để tìm thủ phạm.
Contract Testing (với Pact)
Tách biệt hoàn toàn (Decoupled)
FE và BE test độc lập. Chẳng cần bật BE khi test FE, cũng chẳng cần giao diện FE khi test BE. Chúng đối chiếu nhau qua một "Hợp đồng JSON".
Nhanh như Unit Test
Chỉ kiểm chứng tính đúng đắn của "Cấu trúc dữ liệu giao tiếp" (Schema/Types) thay vì kiểm tra logic luồng chức năng đi sâu vào DB. Trả về kết quả trong vài mili-giây.

Cách Pact hoạt động: Consumer-Driven
Quy trình hướng Người tiêu dùng (Consumer-Driven Contract). Frontend mới là vua.
Giai đoạn 1: Consumer (Ví dụ: React UI)
1
Định nghĩa kì vọng
Viết script (Unit Test) định nghĩa rõ tôi muốn gọi API GET /products và mong đợi nhận được mảng chứa field `price` (Number).
2
Chạy Test & Pact Mock
Pact tạo Mock Server dựng sẵn trả về dữ liệu ảo cho FE để pass Unit Test nội bộ.
3
Sinh ra Contract (Pact File)
Pact tự động kết xuất các kì vọng đó thành file JSON (Hợp đồng giao tiếp) chia sẻ cho BE.
Giai đoạn 2: Provider (Ví dụ: Node.js Backend)
4
Nhận Contract
Backend lấy file JSON Hợp đồng đó về máy (qua thư mục chung hoặc Pact Broker).
5
Pact Replay (Verification)
Pact tự động đóng vai FE, bắn các Request đã ghi trong Hợp đồng thẳng vào server Backend thật.
6
So sánh đối chiếu
Pact kiểm tra xem Response thực tế từ Backend có khớp với yêu cầu của Frontend không. Nếu đổi price thành product_price -> Báo Fail tắp lự.

Pact Mechanics & Lưu ý Bảo mật
Những cơ chế cấu hình nâng cao và điểm mù cần tránh khi dùng Pact.
Vấn đề / Cơ chế Giải thích & Cách xử lý
Bỏ qua Provider States Thiếu trạng thái ban đầu khiến Backend test hay thất bại. VD: FE đòi kiểm tra thông tin User 123, nhưng DB lúc đó đang trống rỗng. Cơ chế State Handlers: Viết script chạy trước để "bơm" User 123 vào DB trước khi Pact Verify.
Lỗi Token hết hạn (401) File JSON hợp đồng lưu lại Token cũ rích của FE sinh ra hôm qua. Hôm nay BE Verify báo lỗi 401 Unauthorized. Cơ chế Request Filters: Dùng hook của Pact để chặn request lại, cạo bỏ token cũ và nhét token mới tinh vào trước khi gửi đi.
Rò rỉ dữ liệu (Postel's Law) Pact tuân theo Định luật Postel: "Khoan dung với những gì bạn nhận được". Nếu Backend lỡ làm lộ trường password_hash, Pact vẫn BÁO PASS xanh rờn (vì nó chỉ quan tâm các trường FE cần đã có đủ, dư thì kệ). Tuyệt đối không dùng Pact để Security Test!

Vai trò của CI/CD trong API & Contract Testing
Đưa việc kiểm thử vào quy trình Vòng lặp Phản hồi Nhanh (Fast Feedback Loop).
Hạn chế của Kiểm thử Thủ công
Sai sót do yếu tố con người (Human Error)
Khi đối mặt với áp lực thời hạn bàn giao (deadline), kỹ sư dễ bỏ sót hoặc bỏ qua việc thực thi đầy đủ các bộ kịch bản kiểm thử API lớn.
Sai lệch môi trường (Environment Drift)
Kịch bản kiểm thử chạy thành công ở máy cá nhân nhờ các cấu hình cục bộ, nhưng dễ thất bại khi triển khai lên máy chủ do thiếu dữ liệu hoặc cấu hình khác biệt.
Giải pháp Tự động hóa với CI/CD
Môi trường chuẩn hóa (Clean Environment)
GitHub Actions khởi tạo một máy ảo độc lập và sạch hoàn toàn. Code kiểm thử chạy thành công tại đây đảm bảo tính độc lập và không phụ thuộc cấu hình cá nhân.
Chốt chặn Chất lượng tự động (Quality Gate)
Hệ thống tự động ngăn chặn việc gộp mã nguồn (Merge Pull Request) nếu Newman phát hiện lỗi logic API hoặc Pact phát hiện vi phạm hợp đồng cấu trúc.

Quy trình tuần tự của Job test-api thực thi ngay khi lập trình viên Push code.
1. Sinh hợp đồng & Khởi chạy Server
1
Pact Consumer Tests
Chạy consumer tests sinh ra file contract JSON mới nhất đảm bảo frontend đã thỏa mãn.
2
Boot Backend Server
Lệnh node server.js & kích hoạt server ngầm trên port 3000 ảo của GitHub.
3
Wait-on Module
Dùng tool thăm dò npx wait-on http://localhost:3000 để hold quy trình lại cho đến khi Server sẵn sàng nhận Request.
2. Thực thi & Xuất báo cáo
4
Newman API Testing
Newman thực thi toàn bộ kịch bản kiểm thử API tích hợp để xác minh tính chính xác nghiệp vụ của EShop.
5
Pact Provider Verification
Chốt chặn cuối cùng: Kiểm chứng backend thực tế với các cam kết cấu trúc trong JSON.
6
Upload HTML Reports
Chỉ thị if: always() đảm bảo lưu trữ báo cáo HTML và logs kiểm thử làm Artifacts kể cả khi có bước thất bại.
